# V6 — Idempotency

**Go concepts:** a `map` used as a derived index over durable state (key → id)
inside the lock that already serializes writes; a check-and-insert that is
atomic because the check and the write share one critical section; `omitempty`
for a field that must not appear on records written by earlier versions; and
`slices.Equal` for comparing intent without rebuilding the request.

**Why this version exists:** V5 makes execution at-least-once, so a crash can
repeat a job's side effect — and a client whose POST timed out can submit the
same work twice and get two jobs. V6 closes the second hole: a client may
attach an `Idempotency-Key` to a submission, and a retry with that key returns
the original job instead of creating and running a second one. Together the two
versions give a contract worth stating precisely:

| | Guarantee |
|---|---|
| **Creation** (V6) | at-most-once per key: one key, one record, one enqueue |
| **Execution** (V5) | at-least-once: an interrupted attempt runs again |

Claiming "exactly-once" for the whole system would be a lie until a job can be
claimed by one worker and resumed without redoing its side effect. V6 says what
it can prove.

## The key is part of the record

```go
IdempotencyKey string `json:"idempotency_key,omitempty"`
```

The key lives on the record rather than in a side table for the same reason
`LastHeartbeat` does: one file, one mutex, one atomic rename. A second
`idempotency.json` could not be written atomically together with `jobs.json`,
so a crash between the two writes would leave a key pointing at nothing — the
opposite of this version's lesson. `omitempty` means every file written by
V1–V5 still loads, and unkeyed records are byte-identical to before.

The lookup index is **derived, never stored**: `Create` builds
`map[string]string` (key → id) from the records it just loaded, inside the
lock. That is O(n) per keyed submission, which is the honest cost of a JSON
file; a persisted index is a database-shaped answer for a version that has a
database.

## Admission and update are different operations

`Store` gains a second write path:

```go
// Create inserts r unless a stored record already carries its key.
// stored is the winning record; created reports whether r was written.
func (s *Store) Create(r Record) (stored Record, created bool, err error)
```

`Save` stays the whole-record update path used by the worker and recovery;
`Create` is the admission path used only by `POST /jobs`. Two names because
they answer two different questions: "here is the record's new state" versus
"may this submission become a record at all?".

`Create`, under the existing `s.mu`:

1. Load the map.
2. Reject an id that already exists: `Create` never updates, so an id
   collision is a caller bug rather than a silent overwrite.
3. If `r.IdempotencyKey != ""`, build the key → id index. Two records sharing a
   key in a hand-edited file is corruption, not a tie to break: return an
   error naming both ids. A map is what makes the collision visible at all.
4. If the key is already present, return that record with `created=false` and
   **write nothing**.
5. Otherwise apply the same transition check and field ownership as `Save`,
   insert, and `writeLocked` once. Return the record with `created=true`.

`Save` refuses to introduce a *new* record that carries a key: that is
`Create`'s job, and allowing it would let a whole-record save duplicate a key
without anyone editing the file. Unkeyed seeds stay allowed — that is how the
V1–V5 tests and direct setup build a store.

Nothing about this needs a second lock, a try-lock, or a retry loop: the check
and the insert happen inside the critical section that already makes writes
serial.

## Field ownership: the key survives whole-record saves

`Save` never writes `IdempotencyKey` on an existing record — it keeps the
stored value, exactly as it keeps `LastHeartbeat`. The worker and recovery
save snapshots; a snapshot built before the key existed (or any caller that
constructs a record by hand) must not be able to erase identity. Only `Create`
sets a key, and only when the record is new.

## The HTTP contract

`POST /jobs` accepts one optional header:

- **`Idempotency-Key`** — opaque bytes. No trimming, no case folding: two keys
  are equal iff their bytes are. Missing or empty means no dedupe, so every
  existing client keeps V1–V5 behaviour. Longer than 255 bytes is a 400, so a
  client cannot grow `jobs.json` without bound.

Order inside the handler: decode → validate command → generate id → `Create` →
enqueue. Validation comes **before** `Create`, so a malformed submission never
binds its key; a later valid retry under the same key still creates the job.

| Outcome | Status | Body | Enqueued? |
|---|---|---|---|
| New keyed or unkeyed job | 202 | the new pending record | yes |
| Replay, same command | 200 | the stored record, whatever its status | **no** |
| Same key, different command | 409 | error | no |
| Key longer than 255 bytes | 400 | error | no |
| Undecodable or invalid command | 400 | error | no; no record, no key |

200 versus 202 is deliberate: a replay accepted nothing new, so the created
status would overstate it. The body is the stored record, so the client sees
the real status (`pending`, `succeeded`, `failed`, `cancelled`) without a
second GET.

Command comparison uses `slices.Equal`. The 409 policy lives in `api`, not in
`store`: the store is transport-agnostic and only knows "this key already
names that record". `api` is the only caller of `Create`, so the policy has one
home.

## Semantics

- **A replay never enqueues.** If the original POST saved the record but its
  enqueue failed (503), retries keep returning that pending record and V5's
  startup recovery is what eventually runs it. Re-enqueueing cannot
  distinguish "never queued" from "queued, response lost", and running a job
  twice is strictly worse than a stall that a restart repairs. A retry of a
  503 is therefore not a guaranteed execution, only a guaranteed identity.
- **Keys never expire.** Expiry needs a clock and a retention policy; neither
  is a V6 need. A key keeps naming its record for the life of the store.
- **Only keyed submissions dedupe.** The CLI (`forge <cmd>`), `GET`, and
  `DELETE` are unchanged; a header on those routes is ignored.
- **Dedupe is per store, not per command.** Two different keys submitting the
  same command are two jobs; that is the caller's decision, not ours.

## Deliverables

- `internal/store`
  - `Record.IdempotencyKey string` (`json:"idempotency_key,omitempty"`).
  - `Create(Record) (Record, bool, error)` as specified above; it rejects an
    existing id instead of updating.
  - `Save` preserves the stored key on an existing record and refuses to
    create a new keyed one.
  - A shared locked insert used by both `Save` and `Create`, so the transition
    check and ownership rules exist once.
  - Duplicate keys in a loaded file are an error that names both ids.
- `internal/api`
  - `createJob` reads `Idempotency-Key`, enforces the 255-byte cap, calls
    `Create`, and answers 202/200/409 per the table.
  - No new routes; `GET`/`DELETE` untouched.
- `cmd/forge`
  - No flag changes. Recovery and the worker carry keys without knowing them.
- `README.md`, `docs/LEARNING.md`
  - README: the idempotency contract, the header example, and the
    creation-versus-execution table.
  - LEARNING: V6 entry in the established format.

## Test checklist

- Store: a second `Create` with the same key returns the first record,
  `created=false`, and leaves the file byte-identical.
- Store: different keys create two records; an empty key never dedupes.
- Store: a key is found again after constructing a new `Store` over the same
  directory (restart).
- Store: `Save` with a record that lacks the key preserves the stored key.
- Store: `Create` on an existing id is refused and writes nothing (keyed and
  unkeyed).
- Store: `Save` cannot introduce a new keyed record, so it cannot manufacture
  a duplicate key.
- Store: a hand-edited file with two records sharing a key makes `Create` fail
  with both ids in the message.
- Store: N goroutines `Create` the same key at once — exactly one
  `created=true`, all return the same id, the file holds one record, and
  `-race` is clean.
- API: two POSTs, one key, same command → 202 then 200, identical id, one
  stored record, and exactly one record reaches a worker.
- API: same key with a different command → 409 and the stored record is
  unchanged.
- API: a 256-byte key → 400 and nothing stored.
- API: an invalid body carrying a key stores nothing; a valid retry with that
  key then creates the job (the failed attempt did not burn the key). The same
  holds for a body with trailing data after the JSON object.
- API: concurrent POSTs with one key → one 202, the rest 200, one id, one
  stored record.
- e2e (`cmd/forge`): two POSTs with the same header execute the command once
  (the command's side effect is counted, not the status), and the second
  response is 200 with the first job's id.
- e2e (`cmd/forge`): submit with a key, wait for `succeeded`, restart `serve`
  on the same data directory, resubmit the same key → 200 with the original
  terminal record and no second execution.
- All V0–V5 tests still pass.

## Out of scope

Key expiry or a TTL, idempotency for the CLI or for `DELETE`, hashing the whole
request (V6 compares the command), a persisted key index, at-most-once
execution (a claim/lease), retry-safe side effects inside the command, and
multi-process coordination (V11).
