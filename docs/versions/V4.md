# V4 — Retries + cancellation

**Go concepts:** `context.Context` propagation (first parameter, down the whole
call chain), `context.WithCancel`, `context.WithTimeout`,
`context.WithoutCancel`, `exec.CommandContext`, `time.NewTimer` in a `select`,
exponential backoff, and `defer` as the cleanup mechanism (`cancel`,
`timer.Stop`, registry release).

**Why this version exists:** V3 runs jobs concurrently but treats every failure
as final and every job as immortal. A flaky command gets one chance; a job that
hangs occupies a worker forever; Ctrl-C is the only way to stop anything. V4
gives a job a lifetime: it is retried a bounded number of times with growing
delays, it can be cancelled by a client, and it runs under a deadline. This is
where `context` stops being "the thing HTTP passes around" and becomes the
mechanism that ties a goroutine, a timer, and a child process to one shutdown
story.

## The three lifetimes

V4 deliberately keeps three contexts distinct, because merging them silently
breaks V3's shutdown contract:

1. **Server lifetime** — `signal.NotifyContext` → `queue.Run`. Cancelled on
   Ctrl-C. Stops dequeuing and stops *retrying*, but an attempt already running
   is allowed to finish, exactly as in V3.
2. **Job lifetime** — one context per job, derived with
   `context.WithoutCancel(serverCtx)` and then `context.WithTimeout`. It drops
   the shutdown signal but keeps values, so a running attempt is not killed by
   Ctrl-C while `DELETE` and the timeout can still stop it.
3. **Attempt** — one `executor.Run` call. Retries operate between attempts, not
   inside one.

## Deliverables

- `internal/executor`
  - `Runner` becomes `Run(ctx context.Context, j job.Job) (Result, error)`;
    `Executor` uses `exec.CommandContext` so cancellation kills the child.
  - A completed context is preferred over the generic error from a killed
    process: after `cmd.Run`, if `ctx.Err() != nil`, wrap `ctx.Err()` so
    `errors.Is(err, context.Canceled)` and
    `errors.Is(err, context.DeadlineExceeded)` work for callers.
  - Stdout/stderr captured before the kill are preserved in `Result`.
  - A context already cancelled before the start returns the wrapped context
    error without running anything.
- `internal/job`
  - `StatusCancelled` added (last value, so no existing number changes), with
    `String` and JSON marshal/unmarshal support.
  - `Status.Terminal() bool` — true for `succeeded`, `failed`, `cancelled`.
- `internal/store`
  - `Record.Attempts int` (`json:"attempts,omitempty"`): how many execution
    attempts were started.
- `internal/queue`
  - Handler type becomes `func(context.Context, store.Record)`; `work` passes
    its lifecycle context to the handler. No other queue behaviour changes.
- `internal/worker` (new package; replaces `cmd/forge.newJobHandler`)
  - `Config{MaxAttempts int, Backoff, Timeout time.Duration}`.
  - `New(st *store.Store, exec executor.Runner, cfg Config, stderr io.Writer) *Worker`.
  - `Handle(ctx context.Context, rec store.Record)` — claim, run, retry,
    persist.
  - `Cancel(id string)` — cancel a running job or tombstone a queued one.
  - **Retries:** up to `MaxAttempts` on any error that is not a cancellation;
    no retry after `DELETE`, timeout, or shutdown. Backoff is
    `Backoff * 2^(attempt-1)`, slept with `time.NewTimer` in a `select` over the
    job context, the server context, and the timer. Before every attempt save
    `running` with the incremented `Attempts` so `GET` shows progress.
  - **Cancellation registry:** `running map[string]context.CancelFunc` plus
    `cancelled map[string]struct{}` (tombstones), both under one `sync.Mutex`.
    `Handle` claims the ID before saving `running`: if a tombstone exists it
    removes it and records `cancelled` without executing. `Cancel` cancels a
    live context, or plants a tombstone when the record is still buffered in
    the queue channel. Only the worker goroutine ever writes a job's status, so
    the store is never the site of a cancel/complete race.
  - **Outcomes:** `DELETE` or timeout → `cancelled`, with `Err` naming the
    cause ("job cancelled" / "job timed out after …"); a failed attempt at
    shutdown → `failed`, no further attempts; a successful process → `succeeded`
    even if cancellation arrived too late.
  - Save failures keep V3's behaviour: reported to `stderr` under a mutex, the
    handler gives up on that record.
- `internal/api`
  - `New(ctx, q, st, canceller)` takes a small `Canceller` interface
    (`Cancel(id string)`), defined where consumed.
  - `DELETE /jobs/{id}`: `404` unknown id, `409` for a terminal record, `202`
    otherwise after asking the canceller, with the current record as the body.
    Cancellation is asynchronous; the record may still read `pending`/`running`
    in the 202 response and must be polled.
- `cmd/forge`
  - `serve` gains `-max-attempts` (default `3`, must be `>= 1`),
    `-retry-backoff` (default `100ms`, must be `> 0`), and `-job-timeout`
    (default `30s`, must be `> 0`). Invalid values print a usage error and exit
    `2`.
  - `runServe` builds a `worker.Worker`, passes `w.Handle` to `queue.Run` and
    `w` to `api.New`.
  - The one-shot `run` path passes `context.Background()` to the executor.

## Test checklist

- Executor: an already-cancelled context returns an error wrapping
  `context.Canceled` and never starts the process.
- Executor: a long-running command (`sleep`) is killed when the context is
  cancelled, the call returns promptly, and `errors.Is(err, context.Canceled)`
  holds.
- Executor: a deadline exceeded returns an error wrapping
  `context.DeadlineExceeded`.
- Job: `cancelled` round-trips through JSON; `Terminal()` is true for the three
  final statuses and false for pending/running.
- Worker: first attempt fails, second succeeds → `Attempts == 2`, `succeeded`
  (fake runner counts calls).
- Worker: every attempt fails → exactly `MaxAttempts` calls, `failed`, last
  error recorded.
- Worker: success on the first attempt → one call, `succeeded`, `Attempts == 1`.
- Worker: `Cancel` during a long backoff (e.g. `time.Hour`) returns immediately
  — the test waits on the handler's completion channel, it does not sleep —
  and the record ends `cancelled` with `Attempts == 1`.
- Worker: `Cancel` while a fake runner is blocked on its context → the runner
  observes cancellation, the record ends `cancelled`.
- Worker: a job cancelled while still queued (tombstone planted before
  `Handle`) never reaches the runner and is stored `cancelled`.
- Worker: deadline exceeded → `cancelled` with a timeout message, no retry.
- Worker: cancelling a record that already succeeded leaves it `succeeded`.
- Worker: shutdown during backoff stops retries and stores `failed`; a running
  attempt is not killed by shutdown (V3 preserved).
- API: `DELETE` on a pending or running record returns `202` and calls the
  canceller; on `succeeded`/`failed`/`cancelled` returns `409`; on an unknown id
  returns `404`.
- CLI: `-max-attempts 0`/`-1`/`nope`, `-retry-backoff 0`/`-1s`/`nope`, and
  `-job-timeout 0`/`-1s`/`nope` each exit `2` with a message on `stderr`
  (table-driven).
- e2e: `sh -c 'exit 1'` with `-max-attempts 2 -retry-backoff 1ms` ends
  `failed` with `Attempts == 2`; `sleep 10` cancelled with `DELETE` ends
  `cancelled` promptly; `sleep 10` with `-job-timeout 100ms` ends `cancelled`
  without a client action.
- Table-driven tests where multiple inputs share one behaviour.

## Out of scope

Jitter or capped backoff, persisting attempt history across restarts,
cancelling queued jobs after a restart (they stay `pending`, as in V3),
per-job retry/timeout policy (V6 atomicity, V7 scheduling), heartbeats and
failure recovery (V5), process groups and orphaned grandchildren (V8),
metrics/logging (V9), draining the queue on shutdown.
