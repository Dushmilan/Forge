# V3 — Concurrent workers

**Go concepts:** `sync.WaitGroup` (fan-out + join; `wg.Add` before `go`,
`defer wg.Done()`), worker pool (multiple goroutines competing to receive
from one channel), shared-state serialization with `sync.Mutex` (`store.Store`
and the `stderr` writer), and the race detector (`-race`) under true worker
concurrency.

**Why this version exists:** V2's single worker goroutine serializes every
job — one slow job (`sleep 10`) blocks up to 64 fast jobs behind it
(head-of-line blocking). V3 turns the single worker into a fixed-size worker
pool: `N` goroutines select from the same `q.jobs` channel concurrently, and
`sync.WaitGroup` ensures `Run` waits for every in-flight worker before
returning on shutdown. This is the version where "concurrent" stops meaning
"one goroutine that never blocks" and starts meaning "many goroutines sharing
state", and where `-race` earns its keep.

## Deliverables

- `internal/queue` changes
  - `Run(ctx context.Context, workers int, handler func(store.Record))`
    spawns `workers` goroutines, each running V2's `select` worker loop
    (`work`), and blocks on a `sync.WaitGroup` until all `workers` return.
  - Competing consumers: all `workers` receive from `q.jobs` without extra
    locking — a Go channel guarantees each enqueued `Record` is delivered to
    exactly one receiver.
  - Shutdown contract (generalized from V2): on `ctx` cancel, every worker
    currently inside `handler(rec)` runs that job to completion; idle workers
    exit immediately; records still in the buffer stay `pending`; `Run`
    returns only after **all** `workers` have returned (`wg.Wait()`).
- `cmd/forge` changes
  - `newJobHandler` serializes writes to `stderr` with a `sync.Mutex` captured
    by the closure: `N` workers now call the handler concurrently, and an
    `io.Writer` (unlike `*store.Store`) is not inherently goroutine-safe.
  - `forge serve` gains `-workers` (default `4`): the number of worker
    goroutines passed to `q.Run`. Values `< 1` print a usage error to `stderr`
    and exit `2` — a pool of zero would accept jobs with 202 and never run
    them.
- Untouched packages: `internal/job`, `internal/executor`, `internal/store`
  (its `sync.Mutex` from V1 now guards concurrent worker saves alongside HTTP
  reads/writes), and `internal/api` production code.

## Test checklist

- Pool concurrency: with `workers = 3`, 3 enqueued jobs enter the handler
  simultaneously (synchronized on a channel barrier — a 1-worker queue would
  deadlock; no `time.Sleep`).
- Head-of-line blocking solved: with `workers = 2`, a slow (gated) job does
  not prevent subsequent fast jobs from running and completing while the
  slow job is still held.
- Multi-worker shutdown: with `workers = 2`, cancel `ctx` while 2 jobs are
  mid-handler and 1 is buffered → releasing only 1 worker leaves `Run`
  blocked; releasing the 2nd worker lets `Run` return; the buffered 3rd job
  is never handed to the handler.
- Backpressure across `N` workers: with `workers = 2`, 2 in-flight jobs plus
  `Capacity` buffered records fill the system; the next `Enqueue` blocks
  until any worker finishes a job.
- Worker handler race safety: concurrent calls to `newJobHandler` (failing
  saves writing to a shared `bytes.Buffer` `stderr`) pass under
  `go test -race`.
- CLI `-workers` validation: `-workers 0`, `-workers -1`, and a non-numeric
  value exit `2` with an error on `stderr` (table-driven).
- `serve` e2e: a fast job submitted behind a slow job reaches
  `StatusSucceeded` while the slow job is still `StatusRunning`, and shutdown
  still joins all workers cleanly.
- Table-driven tests where multiple inputs share one behavior.

## Out of scope

Dynamic worker auto-scaling, per-job concurrency limits or semaphores (V7),
retries and mid-run job cancellation (V4), heartbeats (V5), client-supplied
IDs (V6), queue persistence, draining on shutdown, metrics/logging (V9).
