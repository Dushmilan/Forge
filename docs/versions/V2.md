# V2 — Queue + worker

**Go concepts:** buffered channels as queues, goroutines, a worker loop built
on `select` (a receive races `ctx.Done()`), blocking channel sends as
backpressure, and testing goroutines by synchronizing on channels instead of
sleeping.

**Why this version exists:** V1's `POST /jobs` blocks the HTTP request until
the job finishes — the client pays for the job's whole runtime in request
latency. V2 puts a queue between the API and the executor: the handler
validates, persists, enqueues, and answers immediately; one worker goroutine
drains the queue at its own pace. This is the version where Forge becomes
concurrent, and where the cost of concurrency — races, shutdown, backpressure —
becomes real and must be paid with `-race`, not optimism.

## Deliverables

- `internal/queue` package
  - `Queue` type owning a buffered `chan` of records, capacity 64 (fixed; no
    config — a knob is V7's scheduling story).
  - `Enqueue(ctx, rec)` is a `select` over two cases: a send, and
    `ctx.Done()`. While the worker lives, a full buffer makes the caller wait
    — backpressure reaches the HTTP client for free, no unbounded memory.
    After shutdown the send case can never succeed, so the `ctx.Done()` case
    is what keeps a late POST from blocking forever against a dead worker.
  - `Run(ctx, handler)` starts the worker loop goroutine:
    ```go
    for {
        select {
        case <-ctx.Done():
            return // idle worker exits immediately; queued records are dropped
        case rec := <-q.jobs:
            handler(rec) // finishes the current job, then re-selects
        }
    }
    ```
    Shutdown contract: on context cancel a running job completes, jobs still
    in the buffer are left as `pending`. No drain loop — draining is a later
    version's problem. `ctx.Done()` is the loop's only exit and the channel
    is never closed: senders and the worker share one context, so no send can
    outlive its receiver.
- `internal/api` changes
  - `Server` gains the queue as a dependency (constructor parameter);
    handlers stay thin.
  - `POST /jobs` — validate (400, nothing written), save a `StatusPending`
    record (500 on store failure, unchanged), `Enqueue`, return **202** with
    the pending `Record`. The request no longer waits for execution. If
    `Enqueue` returns a context error (shutdown race), answer **503** with a
    JSON error body — the record already saved stays `pending`.
  - `GET /jobs/{id}` — unchanged code, new meaning: clients observe
    `pending → running → succeeded|failed` as the worker progresses. The
    store's mutex already makes concurrent read/update race-safe.
- Worker handler (owned by `cmd/forge` wiring — a closure over the store and
  executor, passed to `queue.Run`; `internal/api` neither runs jobs nor sees
  the handler)
  - set `StatusRunning`, `Save`; execute through V0's `Executor` seam;
    set the final status from the result, `Save` again.
  - A `Save` failure after execution records the outcome as data, never
    swallows it (V1's honesty rule carries over).
- `cmd/forge` `serve`
  - Constructs the queue, passes it to `api.Server`, and starts
    `queue.Run` with the same context that `signal.NotifyContext` cancels —
    one context, one shutdown story, no `time.Sleep`.

## Test checklist

- Queue: an enqueued record reaches the handler exactly once (synchronize on
  the handler's channel, never `time.Sleep`).
- Queue: cancel `ctx` while idle → `Run` returns; records left in the buffer
  were never handed to the handler.
- Queue: cancel `ctx` mid-handler → the handler completes before `Run`
  returns (finish-current, drop-queued).
- Backpressure: fill the buffer with a held handler, assert a further
  `Enqueue` blocks, free a slot, assert it completes.
- Enqueue after `ctx` cancel returns a context error immediately instead of
  blocking — the no-deadlock guarantee behind the 503.
- API: `POST /jobs` → **202** with `StatusPending` and the record persisted
  before the response; invalid command → 400, nothing written (unchanged).
- API: a submitted job's `GET` transitions to `running` and then to a final
  status, driven by a fake executor that signals start/finish over channels.
- API: store failure at enqueue time → **500**, no enqueue.
- `serve`: worker started, context canceled → server stops and the worker
  goroutine exits (`-race` clean, no leaked goroutine asserted by the loop's
  return reaching a channel).
- Table-driven tests where multiple inputs share one behavior.

## Out of scope

List endpoint, retries, multiple workers/worker pools (V3), priorities (V7),
queue persistence across restarts, draining on shutdown, job cancellation
mid-run (V4), heartbeats (V5), client-supplied IDs (V6), metrics (V9). The
queue is in-process memory; only job records persist.
