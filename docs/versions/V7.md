# V7 — Priority and resource scheduling

**Go concepts:** `container/heap` as an interface *you* implement rather than a
container you import; a min-heap turned into a priority queue by `Less`; a
sequence number as the deterministic tie-break; a buffered channel used as a
counting semaphore; consistent lock ordering to make multi-resource acquisition
deadlock-free; and interfaces declared where they are consumed.

**Why this version exists:** every version so far has exactly one order —
whatever was enqueued first — and exactly one limit — the size of the channel
buffer. A channel is a FIFO and cannot be told otherwise, so a critical job
waits behind a hundred trivial ones. And a worker runs whatever it dequeues, so
a job needing the only `gpu` competes blindly with jobs that need nothing at
all. V7 separates *ordering* from *capacity*: a heap decides what runs next, a
semaphore decides what may run at all.

## Why the channel has to go

`q.jobs` is the queue. That was the right answer while the only requirement was
"one at a time, in order": a buffered channel is a thread-safe FIFO and needs
no lock to be one. It is the wrong answer the moment order stops being arrival
order, because there is no operation on a channel that means "give me the most
important element".

So the queue keeps its own storage — a slice — and keeps the channel only as a
*wakeup*. `container/heap` is not a data structure you instantiate; it is a set
of functions (`heap.Push`, `heap.Pop`, `heap.Init`, `heap.Fix`) that maintain
the heap property on any type implementing `heap.Interface`. The type is ours.

## The heap

```go
// item is one pending record plus the tie-break the record cannot carry.
type item struct {
	rec store.Record
	seq uint64 // arrival order, assigned at Enqueue
}

type pendingHeap []item

func (h pendingHeap) Len() int { return len(h) }
func (h pendingHeap) Swap(i, j int) { h[i], h[j] = h[j], h[i] }

/*
Less is the whole scheduling policy. container/heap is a MIN-heap: it places
the element that is "less than" everything else at the root. Priority therefore
compares backwards — a higher priority must report itself as less — and the
sequence breaks ties forwards, so equal priorities leave in arrival order.
*/
func (h pendingHeap) Less(i, j int) bool {
	if h[i].rec.Priority != h[j].rec.Priority {
		return h[i].rec.Priority > h[j].rec.Priority
	}
	return h[i].seq < h[j].seq
}

func (h *pendingHeap) Push(x any) { *h = append(*h, x.(item)) }

/*
Pop returns the last element: heap.Pop has already swapped the root to the end
and shrunk the slice, so the last slot is the old minimum. This is the one
method whose body looks wrong until you read heap.Pop's contract.
*/
func (h *pendingHeap) Pop() any {
	old := *h
	n := len(old)
	it := old[n-1]
	old[n-1] = item{} // clear the slot: the convention that matters once elements hold pointers
	*h = old[:n-1]
	return it
}

var _ heap.Interface = (*pendingHeap)(nil) // compile-time proof, like `var _ fmt.Stringer`
```

Two things a reader should not have to take on faith:

- **`Less` is comparison, not storage.** Inverting it turns the min-heap into a
  max-heap over any ordered field. There is no `MaxHeap` type in the standard
  library and no need for one.
- **Ties need a rule.** A heap is not stable. With `Less` comparing only
  priority, two `normal` jobs come out in whatever shape the heap happens to
  be in — different on different insert patterns, and not reproducible in a
  test. The sequence number is what makes "FIFO within a priority" true.

## The wakeup

A heap cannot block. There is no `<-h`. The textbook answer is `sync.Cond`, and
V2 deliberately rejected that reflex; V7 does not bring it back. Instead a
one-slot channel carries the wakeup:

```go
notify chan struct{} // capacity 1: a coalescing "something was pushed"
```

`Enqueue` pushes under the mutex, then does a non-blocking send. Workers pop
until the heap is empty, and only then block on `select { case <-ctx.Done():
...; case <-q.notify: ... }`. Coalescing is safe — a token means "there may be
work", never "there is exactly one job" — provided the worker re-signals after
each pop when items remain. Without that re-signal, a second worker can sleep
forever while the first drains the whole heap alone.

`sync.Cond` would have been shorter; it also cannot be `select`ed against
`ctx.Done()`, which is the property every loop in this codebase now depends on.

## Backpressure survives as a semaphore

The old queue was bounded by the channel buffer. A slice is unbounded, so
`Enqueue` could grow memory without limit. The bound comes back as a channel of
capacity `Capacity`, acquired before the push and released when a record is
popped:

```go
slots chan struct{} // Capacity tokens: one per record allowed to be pending
```

This is the version's first semaphore, and it is the honest one: a buffered
channel of *n* tokens is a counting semaphore, acquire is a receive, release is
a send. The API's 503-on-shutdown contract is unchanged, because the acquire
still selects on the caller's context.

Note what the tokens count: *pending* records only. A popped record releases its
slot before it runs, so total in-flight work stays `workers + Capacity`, exactly
as in V3.

## Priority is part of the record

```go
Priority job.Priority `json:"priority,omitempty"`
Resources []string    `json:"resources,omitempty"`
```

```go
const (
	PriorityLow      Priority = iota - 1 // -1
	PriorityNormal                       //  0
	PriorityHigh                         //  1
	PriorityCritical                     //  2
)
```

`iota - 1` is the whole trick: `Normal` must be the zero value so that a record
written before V7, and a client that never mentions priority, both mean "normal"
without a special case. A named type with `String`, `MarshalJSON`, and
`UnmarshalJSON` is the same shape as `Status` in V0 — the second time the idiom
appears is when it should be recognised rather than invented.

`omitempty` on an int omits zero, so a normal job is byte-identical to a V6 job
and old stores keep loading. An unknown name in a hand-edited file fails the
load instead of silently becoming `normal`; the same "corrupt data should be
loud" rule as `Status`.

## Resources: one semaphore per name, one unit each

```go
type Pool struct {
	mu    sync.Mutex
	gates map[string]chan struct{} // name -> free-unit tokens
}

func New(caps map[string]int) *Pool
func (p *Pool) Configured(name string) bool
func (p *Pool) Acquire(ctx context.Context, names []string) (release func(), err error)
```

A job asks for resources by name, each costing one unit:

```json
{"command": ["train"], "priority": "high", "resources": ["gpu"]}
```

`Acquire` sorts the names, then takes one token per name. Sorting is not
cosmetic: two jobs asking for `["gpu","db"]` and `["db","gpu"]` would each hold
one and wait for the other forever. A single global acquisition order makes that
cycle impossible — the same rule as any lock-ordering discipline, applied to
tokens.

If the context ends partway through, `Acquire` returns every token it already
took before reporting the error. A partial acquisition that leaks a token is
how a resource pool dies: the capacity is still configured, but no job can ever
have it.

**Weights are deliberately out of scope.** `{"gpu": 2}` of capacity 4 needs an
*atomic* multi-token acquire. A plain token channel cannot do it: two jobs can
each take half and each block forever. The correct answer is
`golang.org/x/sync/semaphore`, and it is not worth a dependency to demonstrate
a channel-as-semaphore. V7 says one unit per named resource and says so in the
spec rather than pretending the simple version is general.

## Admission: reject what can never run

A job asking for an unconfigured resource would block forever while holding a
worker slot, so `POST /jobs` refuses it:

| Body | Status |
|---|---|
| `resources` names an unconfigured resource | 400 |
| `resources` repeats a name (`["gpu","gpu"]`, capacity 1 would wait for itself) | 400 |
| more than `job.MaxResourcesPerJob` names | 400 |
| unknown `priority` string | 400 (from `Priority.UnmarshalJSON`) |
| otherwise | 202, record echoes both fields |

Structural validation lives in `job.ValidateResources` (shape only: non-empty,
no duplicates, bounded count) and returns wrapped `ErrInvalidJob`, like
`Job.Validate`. Availability is not `job`'s business — it belongs to the pool,
which is why the API holds a tiny consumer-defined interface:

```go
// Resources is the admission seam: the API asks which names exist, never how
// many units are free. Defined here, where it is consumed.
type Resources interface {
	Configured(name string) bool
}
```

`*resource.Pool` satisfies it implicitly — no import of `api` from `resource`,
no registration, no `implements` keyword.

## Where the gate is acquired

`worker.Handle`, after the claim and after the exhausted-budget check, before
the attempt loop:

- **Held across retries.** Three attempts are one job, not three claims on the
  gpu.
- **Acquired under the execution context.** Waiting counts against the job's
  deadline, and `DELETE` can interrupt a job that is waiting rather than
  running. A job cancelled in the gate ends `cancelled` with attempts
  unchanged — it never started.
- **Released with `defer`**, so it returns on success, failure, timeout, and
  cancellation alike. This is V4's cleanup-ledger rule, now covering capacity.
- **An unconfigured name is terminal.** It can only arrive from a hand-edited
  store; retrying cannot fix it, so the record fails with a message naming the
  resource.

Interface, again consumer-side:

```go
// Acquirer is the seam between a job and the resources it needs. worker asks
// for one claim; *resource.Pool is what it gets in production.
type Acquirer interface {
	Acquire(ctx context.Context, names []string) (release func(), err error)
}
```

## Known limit: the gate ties up a worker

A worker that dequeues a `gpu` job and waits for a token is not available for a
job that needs nothing. Under a saturated gpu that is head-of-line blocking, and
the honest fix — let the scheduler hand out only jobs whose resources are free —
is a different design: `Pop` would scan for a satisfiable item, and the heap
would no longer be a pure priority queue. V7 chooses the simple gate and records
the cost. Priority, also, is not a fairness guarantee: a steady stream of
`critical` jobs starves `low`, because nothing ages.

## Semantics

- **A running job is never preempted.** Priority orders pending records only.
- **Cancelling a waiting job works.** The claim is taken before the gate, so
  `DELETE` finds it, and the gate's context ends.
- **Shutdown while waiting leaves the record pending.** It was never running,
  so there is no attempt to spend; V5's recovery requeues it on the next boot.
  This matches V2's existing "buffered records stay pending" rule.
- **Replay compares the whole intent.** V6's 409 compares the command; V7 adds
  priority and resources, because a key that names a `high` gpu job must not be
  replayed as a `low` one. Otherwise one submission would be answered with a
  record it did not ask for.
- **Resources are per process.** Two `forge serve` processes each believe they
  own the capacity; distributing it is V11's problem.

## Test checklist

- Heap: `Less` orders by descending priority, then ascending sequence (table
  test over the four comparisons).
- Heap: pushing and popping through `container/heap` yields priorities in order
  across a shuffled insert, and FIFO within one priority.
- Queue: enqueue low/high/normal with one worker → run order high, normal, low.
- Queue: equal priorities run in enqueue order.
- Queue: `Capacity+1` records still block the sender and the 65th releases on
  the first pop (the V2 backpressure contract, unchanged).
- Queue: a cancelled `Enqueue` never pushes (the existing contract, unchanged).
- Queue: two workers are both woken when two records are pushed (the
  re-signal-after-pop rule).
- Pool: acquire then release restores capacity.
- Pool: capacity 1 serializes two acquirers.
- Pool: `Acquire` blocked on a missing token returns `ctx.Err()` and releases
  every token it already held.
- Pool: `["gpu","db"]` and `["db","gpu"]` with capacity 1 each complete without
  deadlock.
- Pool: an unconfigured name is an error, not a wait.
- Pool: an empty claim is a no-op with a no-op release.
- Worker: a job runs only after its resource is free, and releases on success.
- Worker: a job waiting on a resource is cancelled by `DELETE`, ends
  `cancelled`, and leaves `attempts` at zero.
- Worker: three attempts at one job acquire once (counted by a stub `Acquirer`).
- Worker: an exhausted job never acquires.
- Worker: an unconfigured resource fails the record instead of retrying.
- Store: priority and resources round-trip; a `normal`, resource-free record is
  byte-identical to V6 (no `priority`/`resources` keys); V1–V6 files load.
- Store: a hand-edited unknown priority fails the load.
- API: each 400 in the admission table, with nothing stored.
- API: a valid submission echoes priority and resources; omitted priority reads
  back as `normal`.
- API: a replay with the same key and a different priority is a 409.
- e2e: with one worker and a slow first job, a `high` job submitted second runs
  before a `low` one submitted first.
- e2e: two jobs needing `gpu` with capacity 1 both succeed and never overlap
  (each writes start/end markers to one file).
- All V0–V6 tests still pass.

## Out of scope

Preemption, aging or any anti-starvation policy, weighted resource claims,
scheduler-level admission (popping only satisfiable jobs), resource metrics,
per-job resource release on cancellation *during* execution (the attempt ends,
so the `defer` fires anyway), a configurable queue capacity, and distributed
capacity (V11).
