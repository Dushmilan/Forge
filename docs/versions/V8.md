# V8 — Sandboxed execution

**Go concepts:** `os/exec` as a struct whose fields (`Dir`, `Env`, `SysProcAttr`,
`Cancel`, `WaitDelay`) are yours to set rather than `CommandContext`'s defaults;
a process group as the unit of cancellation, signalled with a negative pid;
`os.MkdirTemp` plus `defer` for filesystem scoping; and preserving the error
chain (`context.Canceled` over `signal: killed`) while the killing mechanism
changes underneath it.

**Why this version exists:** every job so far has run *inside forge itself*:
the child inherits forge's environment, starts in forge's working directory,
and — the part that matters — is killed alone. `exec.CommandContext`'s default
cancel calls `Process.Kill` on the direct child only, so a job that spawns
anything (`sh -c 'sleep 100 &'`) leaves that grandchild running after the job
is cancelled or timed out. V8 gives each run a room of its own (a fresh
directory, a scrubbed environment) and makes cancellation a property of the
whole process tree instead of one pid.

Measured, not assumed: a scratch program running
`sh -c 'sleep 60 & echo $! > pid; wait'` under plain `CommandContext` leaves
the `sleep` alive after cancel (`/proc/<pid>/stat` still `S`), while the same
program with a process group and a group kill leaves it `gone`.

## The room: one directory per run

```go
dir, err := os.MkdirTemp(root, "forge-job-") // root: Executor.SandboxRoot, "" means os.TempDir()
if err != nil {
    return Result{}, fmt.Errorf("job %q: sandbox: %w", j.ID, err)
}
defer os.RemoveAll(dir) // runs after Wait: no process is left writing into it
...
cmd.Dir = dir
```

Three rules, each of which a naive version gets wrong:

- **The name never contains the job id.** `job.Validate` only requires a
  non-empty id; an id like `../../etc` must not choose the path. `MkdirTemp`'s
  random suffix does, and the test that pins this uses a hostile id on purpose.
- **Creation happens after the `ctx.Err()` check.** A cancelled job must not
  touch the OS at all — the order in `Run` stays: validate → context →
  `MkdirTemp` → start.
- **Removal happens after `Wait`.** `defer` registered before `cmd.Run`
  returns runs once the process is gone, so nothing is deleting files a live
  child still has open. Each retry attempt calls `Run` again and therefore
  gets its own clean directory; nothing carries over between attempts.

## The environment: replacement, not addition

```go
cmd.Env = []string{"PATH=" + os.Getenv("PATH")}
```

Assigning `cmd.Env` *replaces* inheritance wholesale — it is not a patch over
the parent's environment, so forge's variables simply do not exist for the
child. Only `PATH` is carried over, and it is forge's own value: `LookPath`
resolves the program name against the parent's `PATH` anyway, so a child that
could not be located would never start. `HOME`, `TMPDIR`, `LANG` and friends
are deliberately absent.

Consequence worth stating in the spec rather than discovering in production:
a relative command like `./script` now resolves *inside the empty sandbox* and
fails. Commands are names on `PATH`, or absolute paths — that was already the
contract of `j.Command[0]` without a shell; V8 just makes it visible.

## The process group: cancellation is a tree operation

```go
cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true} // child leads its own group
cmd.Cancel = func() error { return syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL) }
```

Two facts that only work as a pair:

1. `Setpgid: true` makes the child a process-group leader: its pgid equals its
   pid, and every process it spawns inherits that group by default.
2. `syscall.Kill(-pid, sig)` addresses the *group* — a negative pid is the
   POSIX spelling of "this process group".

Without (1), the child inherits **forge's own** group, and `kill(-childpid)`
targets a group that does not exist (`ESRCH`) — verified experimentally, not
reasoned from the manual. So `Setpgid` and the negative pid go in the same
commit, in the same function, and a test asserts the invariant directly: after
start, `Getpgid(child) == child`.

This is also the point of replacing `CommandContext`'s default `Cancel`: the
default kills one pid; ours kills the group. `cmd.Cancel` is only called after
`Start` succeeds, which is what makes reading `cmd.Process.Pid` inside the
closure safe — the watchdog goroutine that calls it is started by `Start`
itself.

`kill` on an already-empty group reports `ESRCH`. Harmless: the only caller is
the context watchdog, and a job whose context is done is treated as cancelled
by the worker regardless of what `Wait` returns.

## Wait can outlive the kill

Stdout and stderr are captured into `bytes.Buffer` values, not `*os.File`s,
so `os/exec` gives the child a pipe plus a copying goroutine, and `Wait` does
not return until those pipes hit EOF. A grandchild *inside* the group dies with
the group, pipes closed, `Wait` returns promptly. A grandchild that escapes
(`setsid sh -c 'sleep 100'`) starts a new session and group, survives the
kill, and holds the write end of the pipe open forever — `Run` would hang
after cancellation, which is exactly the class of bug V8 exists to remove.

```go
cmd.WaitDelay = waitDelay // const waitDelay = time.Second
```

`WaitDelay` (Go 1.20+) bounds that wait: when the context is done (or the
child has exited) and the delay elapses, `os/exec` closes the pipes itself.
One second, not ten: the group kill is a `SIGKILL` — nothing *inside* the
group needs grace — and a process still holding the stream after a second is
an escapee we refuse to wait for.

The same knob fixes a silent pre-existing hang: a command that exits 0 while
a background child keeps the streams open currently blocks `Run` forever. With
`WaitDelay`, `Wait` returns `exec.ErrWaitDelay`; because the context is not
done in that case, the error surfaces as-is (wrapped with the job id) and the
attempt fails. That is a new failure mode and it belongs in the semantics.

## Known limit: a clean room, not a jail

V8 sets the child's working directory and environment; it does not *constrain*
it. A job can still `cd /` and write anywhere the forge user may write, open
sockets, or `setsid` itself free of the group — the escapee test proves the
last one deliberately. Real confinement (namespaces, cgroups, rlimits,
seccomp, chroot) is a different version with a different charter; saying
"sandboxed" here means *isolated inputs and a scoped kill*, not containment.
The README and this spec both say so, because a sandbox that oversells itself
is worse than no sandbox.

`SysProcAttr.Setpgid` and `syscall.Kill` with a negative pid are Unix-only, so
V8 is Unix-only. The repo runs on Linux; build tags that stub the sandbox out
on Windows would teach build constraints at the cost of never letting the real
code be tested. One file, no tags, a sentence in the README.

## Semantics

- **Every run gets a fresh, empty directory as its cwd,** removed when `Run`
  returns — success, failure, or cancellation. Retries get a new one each
  attempt.
- **The child sees forge's `PATH` and nothing else.** Lookup of the command
  name uses forge's `PATH` either way.
- **Cancel and deadline kill the whole group.** Grandchildren inside the group
  die with the job; `errors.Is(err, context.Canceled/DeadlineExceeded)` still
  holds, because the executor keeps preferring `ctx.Err()` over
  `signal: killed`.
- **Escapees survive; `Run` returns anyway.** A process outside the group can
  outlive the job, but its stream is cut after `waitDelay`, so `Run` returns
  within roughly a second of cancellation instead of hanging.
- **Exit 0 with a still-open stream fails.** `exec.ErrWaitDelay` (wrapped)
  marks the attempt failed rather than blocking forever.
- **A sandbox directory name never derives from the job id.**
- **Unix-only.** No Windows build.

## Deliverables

- `internal/executor`
  - `Executor.SandboxRoot string` field: the parent directory for sandboxes;
    zero value means `os.TempDir()`. `Executor{}` remains a valid `Runner`, so
    `cmd/forge` and every existing caller need no change.
  - `Run` extended in order: validate → `ctx.Err()` → `MkdirTemp` → defer
    `RemoveAll` → configure `Dir`, `Env`, `SysProcAttr`, `WaitDelay`, `Cancel`
    → run. Error wrapping keeps `exec.ErrNotFound`, `*exec.ExitError`, and the
    context sentinels findable with `errors.Is`/`errors.As`, unchanged from V0.
  - `const waitDelay = time.Second`.
  - Package/doc comments explaining the group-kill invariant and the
    `WaitDelay` pipe bound (the Go concepts, per AGENTS.md).
- `cmd/forge` — no code change (zero-value `Executor` picks the defaults).
- `README.md` — status line, ladder row ✅, a `## How it works (V8)` section
  stating the clean-room-not-a-jail limit, Unix-only note.
- `docs/LEARNING.md` — V8 entry in the established format.

## Test checklist

- Sandbox: `sh -c pwd` reports a directory under `SandboxRoot`.
- Sandbox: `SandboxRoot` is empty after a successful run, after a non-zero
  exit, and after cancellation.
- Sandbox: an invalid job and a cancelled-before-start job create **no**
  directory (order rule).
- Sandbox: a job id of `../../evil` still runs inside `SandboxRoot`.
- Sandbox: a non-existent `SandboxRoot` returns an error wrapping
  `fs.ErrNotExist` and starts no process.
- Sandbox: two concurrent `Run`s with one `SandboxRoot` get distinct
  directories, both succeed, and the root is empty afterwards (`-race`).
- Env: a variable set in the forge process (`t.Setenv`) is invisible to the
  child; a `PATH`-resolved command still runs.
- Group: after start, `Getpgid(child) == child.pid` (the pair invariant).
- Group cancel: a job spawning `sleep 60 &` is cancelled; `Run` returns
  wrapped `context.Canceled` and the grandchild is dead (`/proc/<pid>/stat`
  missing or `Z`, polled with a deadline — never a bare `time.Sleep`).
- WaitDelay: a `setsid` escapee holding the pipe does not block `Run`; it
  returns within ~`waitDelay` with wrapped `context.Canceled`, and the
  escapee is proven alive (limit pinned), then cleaned up by the test.
- Regression: missing binary still wraps `exec.ErrNotFound`; non-zero exit
  still yields `*exec.ExitError` with the right `ExitCode`; stdout/stderr
  capture and the before-start context check are unchanged.
- All V0–V7 tests still pass; `go test ./... -race`, `go vet ./...`, and
  `gofmt -l .` are clean.

## Out of scope

Namespaces, cgroups, rlimits, seccomp, chroot, setuid/per-job users, network
isolation, output-size caps (a candidate for a later version), a
`-sandbox-root` flag or any CLI surface (YAGNI — the struct field is the
configuration), persisting the sandbox path in the record, per-job environment
allowlists (`job.Job` stays `{ID, Command}`), Windows support.
