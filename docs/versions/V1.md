# V1 — API + persistent jobs

**Go concepts:** `net/http` handlers, JSON encoding/decoding (`encoding/json`),
Go 1.22 pattern-based routing (`"GET /jobs/{id}"`, `r.PathValue`), file
persistence (atomic write via temp file + `os.Rename`), `crypto/rand` IDs,
`flag.FlagSet` for subcommands, `sync.Mutex` for correctness under
`net/http`'s per-request goroutines, `httptest` and `t.TempDir()`.

**Why this version exists:** a job runner nobody can submit jobs to is a
library, not a system. V1 gives Forge an HTTP face and a memory — jobs can be
submitted over the network and survive the process that ran them. Execution
stays synchronous in the handler: the request blocks until the job finishes.
That honesty is deliberate — when V2 puts a queue in front of the executor,
the upgrade is felt in the latency of `POST /jobs`.

## Deliverables

- `internal/store` package
  - `Record` type: ID, command, `job.Status`, `executor.Result`, error string.
  - `Store` backed by one JSON file (`map[string]Record`), directory passed in.
  - `Save` writes atomically: marshal → `jobs.json.tmp` → `os.Rename`.
  - `Get` returns the record or a wrapped `ErrNotFound` sentinel.
  - A `sync.Mutex` guards the file: `net/http` serves each request on its own
    goroutine, so this is data-race correctness, not premature concurrency.
- `internal/api` package
  - `Server` type holding executor + store; handlers as methods.
  - `POST /jobs` — decode `{"command": [...]}`, validate, run synchronously,
    persist, return **201** with the full `Record`.
  - `GET /jobs/{id}` — return **200** with the `Record`, or **404** with a
    JSON error body.
  - Errors are JSON values (`{"error": "..."}`), never bare 500 text. If the
    job ran but the store rejected it, `POST` answers **500** with the store
    error — the job's outcome is reported as data, not swallowed.
  - IDs are server-generated: 16 random bytes from `crypto/rand`, hex-encoded.
    Client-supplied IDs are V6's (idempotency) story.
- `cmd/forge` gains a `serve` subcommand
  - `args[0] == "serve"` → parse `-addr` with a `flag.FlagSet`, start the
    server; otherwise V0's CLI behavior is unchanged.
  - Shutdown on context/signal — no `time.Sleep`, no busy-wait.
- `internal/job` and `internal/executor` are reused unchanged (V0's `Runner`
  seam and `Validate` do the work they were designed for).

## Test checklist

- Store: `Save` then `Get` from a fresh instance returns the same record;
  `Get` of a missing ID returns a wrapped `ErrNotFound`.
- `GET /jobs/{id}`: existing → 200 + JSON body; missing → 404 + JSON error.
- `POST /jobs`: valid command → 201, persisted with `StatusSucceeded`;
  missing command → 400 and **nothing written**; `sh -c 'exit 3'` → 201 with
  `Result.ExitCode == 3` and `StatusFailed`.
- Concurrency: parallel GETs during a POST stay `-race` clean (justifies the
  mutex).
- `serve`: starts and shuts down on context cancel without sleeping.
- Table-driven tests where multiple inputs share one behavior.

## Out of scope

List endpoint, `PUT`/`DELETE`, client-supplied IDs, SQL, authentication,
async/background execution, job TTL/GC, metrics. V2 moves execution behind a
queue; none of the above preempts it.
